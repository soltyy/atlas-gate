# Gate #144: сетевые ожидания и общий барьер

18.11.2026, рабочая версия Gate 0.4.41, Router 0.8.29. На момент рекона
службы не переключались: Gate PID157470 работает с17.11 21:11:29МСК,
Router PID2881857/2882067 — с14.11 03:34:10/11МСК (06:34+06).
Публикация 0.4.42/0.8.30 не была установкой этих выпусков.

В журнале Gate `context_windows.poll → nodes.refresh → probe → Lock.acquire`
ждёт20секунд и завершается TimeoutError. Проверки health, открытия, prompt,
восстановления и чтения используют тот же узел. Прежний probe после каждого
ожидающего заново вызывал SDK auth/catalog, вместо совместного результата.
Кроме того create держал общий routing lock во время sync всех историй
устройства, refresh всех узлов и проверки прежней истории.

Проверка каналов выполнена без перезапуска и без запросов модели:

- SSH data link PID159584 работает с18.11 04:51:26МСК; журнал перезапусков
  за последние3часа пуст. Оба Router идут через один SSH TCP транспорт.
- Пять коротких ASGI404 запросов к каждому узлу: напрямую9–268мс,
  через туннель128–947мс. TCP mtr на22:8проб, конечный адрес0% потерь,
  RTT98.6–274.9мс. ICMP в одном направлении дал8потерь из12, обратно0/12;
  это не основание переносить66.7% на потери прикладных запросов.
- TCP живого data link показал рост retrans с2857 до2863; на обратном
  конце были1665накопленных retrans. Это подтверждает сетевые повторы,
  но накопленный счётчик не устанавливает время начала/единственную причину.
- `/health` Router включает запуск CLI auth; его5–16секунд нельзя считать
  чистым временем канала. `/harness/health` также включает refresh узлов.
- На Router наблюдался CPU steal24–40%; свободно около4ГиБ RAM,
  iowait0. Это отдельный фактор среды, без доказанного вклада в каждый вызов.

Исправление: совместный in-flight probe с локальной отменой ожидателя;
новая явная проверка после завершённого probe по-прежнему запрашивает узел.
Ошибочный probe удаляет устаревший snapshot. CREATE проверяет только
разрешённые кандидаты своего маршрута/закреплённый узел, выполняет сеть
перед общим замком; внутри остаются повторные проверки key/body, владельца,
scope, SDK identity, лимитов и атомарный durable резерв без await.
Обычный CREATE не сканирует старые чаты; фоновая сверка сохранена,
при достижении лимита выполняется дополнительная сверка устройства вне замка.
Prompt/compact проверяют закреплённый Router, а не независимый узел.

Результаты и дальнейшая приёмка фиксируются в тикете и выпуске.
Во время восстановления подтвердилось ещё одно препятствие: canonical
deploy требовал пустого Gate I/O до создания admission barrier. При постоянном
притоке запросов такой порядок не позволял начать drain. Проверка перенесена
на существующий барьер после закрытия новой admission; перед остановкой
пустой Gate I/O и все SDK-счётчики по-прежнему обязательны. Версия старого
Gate берётся из аутентифицированного runtime вместо очереди health→discovery.
RED→GREEN: проверка установки требовала наличия admission fence при каждом
контроле Gate I/O. 35 Linux проверок deploy/rollback/ingress прошли.

Это не утверждение о полной причине56минутного EDT executor, потерях TLS,
неверном DNS либо о выполнении всех действий старого хода. Завершённые
инструменты не запускаются заново; потерянные ACK сверяются прежними ключами.
