# Новый сервер без прерывания текущего production

Решение пользователя от 05.10.2026: Gate и Router развернуть вместе на другом
сервере. Текущий production продолжает работать. Это первоначально независимый
контур, а не активная копия production Store.

## Первый запуск

На новом сервере две службы/процесса: Router на loopback:8765, Gate на 8766 за
отдельным HTTPS адресом. ОС, адрес, service account и способ подключения уточняются
до установки. Использовать фиксированные commits кандидатов обоих проектов и
`uv sync --locked`; установка описана в [DEPLOYMENT.md](DEPLOYMENT.md).

Новый Router получает собственный NODE_ID, NODE_DB и SDK home. Новый Gate — свои
SQLite, signing key, keyring secret, admin token и тестовую организацию/устройство.
Endpoint токен Router доступен только локальной конфигурации Gate; SDK вход остаётся
на новом Router. Секреты передаются защищённым способом и не попадают в Git/логи.

Не копировать live production БД, signing key или SDK home для параллельного
активного использования. Не менять production службу, профиль клиентов, ingress,
DNS или регистрацию устройств в ходе этой установки. Тестовый клиент явно выбирает
новый Gate. Для одного сервера direct loopback штатен; NAT/mTLS канал нужен при
добавлении удалённых Router.

## Последовательность приёмки

1. Проверить ОС/runtime/порты/service account и постоянные каталоги данных.
2. Запустить Router на stub и отдельный Gate; проверить health/node discovery,
   enrollment/profile, models, session/tools/events/usage и owner isolation.
3. Выполнить SDK вход на новом Router и реальные Claude/Codex проверки, включая
   stop/subtasks, compact/resume, restart и потерю ACK. Для двух backend установить
   отдельный экземпляр Router на backend с отдельными портами/ID/journal/profile.
4. Проверить EDT на тестовом Gate, reboot/autostart, ACL/TLS, backup/restore и
   наблюдение за нагрузкой, unknown operations и сроками сертификатов.
5. Только после приёмки согласовать перевод клиентов и перенос данных отдельно.
   До этого production остаётся на прежнем Gate/Router.

Если новый SDK входит в тот же подписочный аккаунт, его проверки расходуют общую
квоту с production. Account_group нового Gate координирует только подключённые к
нему узлы; старый независимый Gate он не контролирует. Для полной изоляции нагрузки
использовать отдельный тестовый аккаунт; на первом шаге достаточно stub.

## Дальнейший переход

Порядок snapshot/сохранения доверия устройств описан в [MIGRATION.md](MIGRATION.md).
Изолированное развёртывание не требует production drain; drain/остановка могут
понадобиться позже для согласованного переноса текущих данных. Автоматический перенос
активных HTTP SID/SDK истории на новую машину не заявляется. Старые беседы могут
завершаться на старом контуре, а новые открываться на новом при явном разделении
клиентов; это не синхронизация двух Gate.

До перехода rollback нового контура — остановка только новых служб и возврат
тестового клиента к прежнему endpoint. После перехода нужен отдельный план сверки
новых device/SID/usage записей; нельзя слепо восстановить старую копию БД.
