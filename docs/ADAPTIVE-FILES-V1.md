# Adaptive files v1

Маршруты для старых оригиналов по запросу `atlas_file` в активном подписочном ходе. Gate #131, Router #121, Harness #549.

## Согласование

При обычном create/resume Harness может предложить `"adaptiveFiles":{"version":1,"branchId":"<stable branch id>"}`. Выбор маршрута, модели, SDK и истории — прежний. Создание подтверждает новый канал полем `adaptiveFiles` с `version`, `branchId` и `bootId` только при доступных SDK-файлах и durable Router. Gate с исходящим connector требует protocol 3. `sdkTools.files` сохраняет прежнее значение.

Клиент принимает только ACK своего branch. Проверка живой привязки — `GET /harness/agent/sessions/{sid}/files/adaptive`, с ответом `{"adaptiveFiles":{"version":1,"branchId":"...","bootId":"..."}}`. Для прямого Router префикс `/v1/sessions/{sid}`. Отсутствие ACK или 404/409 при согласовании означает прежний путь с `/files`. Временная ошибка чтения требует сверки состояния привязки.

Для каждого adaptive prompt клиент добавляет `"adaptiveFiles":{"version":1,"bootId":"<ack boot>"}` в исходное тело обычного `POST .../prompt?mode=async`. Хранить это поле вместе с исходным телом и ключом. Сессия может выполнять обычные ходы без этого поля. При изменении boot или утрате привязки заново согласовать возможность через штатный resume. Новый prompt — после сверки исходного intent по обычному контракту. Ответы старого вызова остаются привязанными к его boot и SID.

## Событие и ответ

В обычных SSE и `turns/{turnId}/events?after=N` приходит `type: "adaptive_file_request"` с полями `version`, `requestId` (UUID), `turnId`, `callId`, `branchId`, `bootId`, `operation`, `waitMs` (окно ожидания запроса файла) и `expiresAt` (Unix seconds). Для `operation: "original"` дополнительно приходят `sha256` и `needsBytes`. Использовать `sid` того же потока. Это событие слоя файлов; `sdk_tool_started/completed` остаются событиями отображения.

`POST /harness/agent/sessions/{sid}/files/adaptive/{requestId}` с `Idempotency-Key: <requestId>`. Во всех ответах повторить `bootId`, `branchId`, `turnId`, `callId`; для оригинала повторить `sha256`.

| Запрос Router | Поля ответа Harness сверх идентификаторов |
| --- | --- |
| `catalog` | `status: "available"`, `files: [{sha256, filename, mediaType, sizeBytes}]`. `mediaType` можно опустить. Пустой доступный каталог — `files: []`. |
| `original`, `needsBytes: true` | `status: "available"`, `data` — base64 исходных байтов после проверки SHA. |
| `original`, `needsBytes: false` | `status: "available"` после проверки разрешения. Оригинал уже есть в Router. |
| Нет разрешения или оригинал недоступен | `status: "unavailable"` и идентификаторы. |

Каталог собирается из разрешённых метаданных. Проверить свежие ACL по SID/ветке и SHA при каждом запросе, включая попадание в кеш. Передавать только допустимые имена и метаданные, без локальных путей. При отзыве прав после локальной проверки и до отправки отправить отказ. Существующие вложения текущего сообщения, подготовка референса для `atlas_image`, PDF, `steer` и `tool_result` продолжают прежний обмен. Отсутствующие старые референсы по требованию поддерживает `atlas_file python`.

## Квитанция и восстановление

Успешный POST и повтор с тем же ключом/телом возвращают `{version:1,status:"accepted",outcome:"available"|"unavailable",requestId,bootId,branchId,turnId,callId[,sha256]}`. Это подтверждение ответа Harness на запрос файла. Исполнение `atlas_file` и итог хода проверяются обычными событиями.

При потерянном ответе сначала `GET .../files/adaptive/{requestId}`. HTTP 200 возвращает квитанцию либо `{"status":"pending","request":{...исходное событие...}}`. Повторить только исходный POST с тем же SID/boot, ключом и телом при живом pending и по-прежнему действующем разрешении. Соблюдать Retry-After при наличии. HTTP 409 от закрытого запроса и 410 от истёкшей квитанции прекращают досыл. 422 требует исправить ответ, пока он не принят. После Stop игнорировать pending-события из старой страницы истории. При рестарте читать сохранённую квитанцию, а исходные ожидания считать закрытыми. Продолжение SDK и запись истории управляются обычным recovery; новый вызов модели получает новый requestId.

В приёмке сначала проверить два соседних хода без старых файлов, затем один отсутствующий оригинал и попадание в кеш. Добавить Stop, недоступность файла, отзыв доступа, чужую ветку, потерянную квитанцию и повторное чтение курсора. На старых Gate/Router и в обычных API-маршрутах работает прежний код Harness.
