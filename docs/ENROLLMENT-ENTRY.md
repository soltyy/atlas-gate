# Внешняя ссылка подтверждения устройства

Gate возвращает `/harness/admin/?user_code=…` в `verification_url`. Это штатный
вход администратора в подтверждение регистрации. Страница должна открываться
через публичный HTTPS; код выделяет заявку, но не даёт административных прав.
Если срок кода истёк, клиент начинает новую регистрацию. Само открытие ссылки
не одобряет устройство.

Для Nginx включить [deploy/nginx-gate-admin.conf](../deploy/nginx-gate-admin.conf)
в HTTPS server вместо общего `location ^~ /harness/admin { return 403; }`.
Gate слушает только loopback, `ATLAS_TRUST_LOCAL=false`, `ATLAS_TOKEN` непустой.
Общий proxy location продолжает передавать исходный IP своим X-Forwarded-For.

HTML и ассеты — отдельные location: они убирают X-Forwarded-For, чтобы пройти
существующую loopback-проверку статической страницы. Admin API остаётся в обычном
proxy location, проверяет ключ и сохраняет IP клиента. Не копировать исключение
статической страницы на весь `/harness/admin/` или `/harness/enroll/`.

Администратор открывает «Ключ доступа», вводит свой ключ, выбирает заявку с кодом,
проверяет устройство/сотрудника/организацию и явно одобряет. Обычный пользователь
передаёт код администратору; общий административный ключ ему не выдаётся.

Перед изменением сохранить конфигурацию вне репозитория. Выполнить `nginx -t`,
затем graceful `systemctl reload nginx`; Gate и Router не перезапускать.
Проверить извне HTML с query и все его ассеты (200), admin devices/enrollments
и POST enroll/approve без ключа и с неправильным ключом (401).
Проверку approve делать только с фиктивным кодом и без действующего ключа.
Откат: восстановить сохранённый virtual host, `nginx -t`, reload.

Python-пакетов и контрактов Router из других выпусков.
