# Резервный путь Gate через Финляндию

Резерв включается отдельно по решению оператора. Оба пути заканчиваются на тех же процессах Router на `vdska`. Gate сохраняет `node_id`, привязки сессий и журнал команд. Рабочий прямой туннель обслуживает `atlas-gate-link.service`.

| Узел | Рабочий порт на Gate | Порт на Gate через FI | Порт селектора для проверки | Назначение на `vdska` |
| --- | ---: | ---: | ---: | --- |
| `vdska-codex` | 8765 | 28765 | 38765 | `127.0.0.1:8765` |
| `vdska-claude` | 8768 | 28768 | 38768 | `127.0.0.1:8768` |

Все порты таблицы слушают на `127.0.0.1`. До явного изменения адресов Gate его рабочие запросы продолжают идти напрямую.

## Подготовка доступа

Выделенная учётная запись `atlas-router-link` на Gate хранит ключ `/etc/atlas/router-standby/standby_ed25519` (владелец учётная запись, режим `0600`). Оба сервера принимают его публичную часть для отдельного пользователя `atlas-router-link`. На FI источник разрешённого подключения — IP Gate, назначение проброса — SSH-порт Router. На Router источник — FI, назначения — только два loopback-порта Router из таблицы. У обеих учётных записей допускается только локальный TCP-проброс, без оболочки, PTY, обратных пробросов, X11 и SSH-агента. Служебный ключ не покидает Gate.

В `/etc/atlas/router-standby/known_hosts` закрепите подтверждённые по независимому каналу ключи ED25519 под именами `atlas-standby-fi` и `atlas-standby-router`. Сверьте отпечатки из операторской карточки #153. Каталог конфигурации, `known_hosts` и `ssh_config` принадлежат root, SSH-служба может их читать. Для `runtime.env` задайте `root:root 0600`. PID 1 передаст его службам, которым нужны токены.

## Проверка до подключения Gate

На Gate нужны systemd, OpenSSH, Python 3 и HAProxy 2.8 с Lua. Исполняется отдельный экземпляр HAProxy. При установке пакета учтите автозапуск дистрибутивного сервиса. В `runtime.env` задайте для обоих префиксов `CODEX_` и `CLAUDE_` переменные `NODE_ID`, `DIRECT_PORT`, `STANDBY_PORT`, `LISTEN_PORT` по таблице. Передайте соответствующие `CHECK_TOKEN` через одобренное хранилище секретов.

Из каталога этой инструкции установите подготовленные файлы на Gate. Перед запуском убедитесь, что порты `28765/28768` и `38765/38768` свободны и существующие определения этих трёх unit соответствуют плану.

```sh
install -d -m 0755 /usr/local/lib/atlas-router-standby
install -m 0644 preflight.py haproxy.cfg path_checks.lua /usr/local/lib/atlas-router-standby/
install -m 0644 ssh_config /etc/atlas/router-standby/ssh_config
install -m 0644 atlas-router-standby-link.service atlas-router-standby-enrol.service atlas-router-selector.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now atlas-router-standby-link.service
systemctl start atlas-router-standby-enrol.service
```

Дождитесь успешного завершения `enrol`. Если SSH ещё подключается, дождитесь готовности и повторите только сверку. Для каждого Router она выполняет три аутентифицированных чтения `/v1/node/identity` в порядке direct → FI → direct и требует совпадения протокола, ожидаемого узла и экземпляра. Только совпадение обеих пар атомарно обновляет `/var/lib/atlas-router-standby/verified-boots.env`. Файл переживает перезапуск Gate. Пишет его отдельная служба сверки, у HAProxy доступ только к значениям окружения.

```sh
systemctl enable --now atlas-router-selector.service
systemd-run --quiet --wait --pipe \
    -p EnvironmentFile=/etc/atlas/router-standby/runtime.env \
    -p EnvironmentFile=/var/lib/atlas-router-standby/verified-boots.env \
    /usr/bin/python3 -I /usr/local/lib/atlas-router-standby/preflight.py --check-selector
```

Проверка должна вернуть `HTTP 200, identity OK` для обоих Router. При первом старте селектор ждёт первого успешного чтения идентичности на доступном пути. Повторный запуск селектора использует сохранённые идентификаторы. Если доступен только прямой путь, он обслуживает запросы. Если доступен только FI, оба узла могут обслуживаться через резерв с ранее подтверждённым `bootId`. Неизвестный `bootId` на FI закрывает соответствующий вход. Отказ каждого пути при старте проверяет `tests/ops/router_standby_canary.py` в изолированном loopback-стенде. Для контрольной проверки FI на Gate используйте второй экземпляр селектора на свободных портах с закрытыми прямыми входами, без вмешательства в рабочий туннель.

## Переключение и возврат

Селектор периодически вызывает аутентифицированный `GET /v1/node/identity` на прямом пути и через FI параллельно. Router 0.8.37 возвращает `nodeId`, `bootId` и `protocolVersion` до обращения к SDK. Селектор сверяет все три поля. При транспортном тайм-ауте, 502, 503 или 504 он сразу запускает ещё одну пару проверок для этого Router. Если обе снова отказали, следующая проверка пройдёт в штатном цикле. HTTP 409 или ответ с чужим идентификатором немедленно закрывает путь. Обнаружение чужого процесса напрямую также закрывает путь через FI до подтверждения закреплённого процесса напрямую или повторной регистрации. Проверка ограничена 5 секундами и ответом идентификации размером 2 КиБ. Для рабочих потоков сохранены нулевые `timeout client` и `timeout server`. Все проверки используют отдельные соединения без повторов HTTP-клиента.

В свободное окно сохраните текущие адреса узлов и проверьте отсутствие активных ходов по штатной процедуре поставки. На этапе переключения замените только `url` соответствующих узлов Gate на `http://127.0.0.1:38765` и `http://127.0.0.1:38768` и примените конфигурацию штатным способом. Проверьте опрос обоих узлов самим Gate и снимите свою паузу приёма новых ходов. При откате верните `http://127.0.0.1:8765` и `http://127.0.0.1:8768` тем же способом, проверьте оба узла и возобновите приём.

Селектор выбирает путь для нового TCP-соединения. После разрыва уже открытого потока приложение дочитывает события исходного хода с последнего подтверждённого `seq`. Для команды с неопределённым исходом Gate запрашивает квитанцию на исходном Router по прежнему ключу. Переключение транспорта не инициирует повторный POST или запуск инструмента.

При плановом перезапуске Router меняется `bootId`. Для возобновления доступа выполните `systemctl start atlas-router-standby-enrol.service` после проверки обоих экземпляров. Применяйте новые закреплённые идентификаторы штатной процедурой в свободном окне. При откате к исходной топологии верните прямые адреса узлов в Gate и проверьте оба Router перед отключением селектора.

## Обновление уже работающего селектора

Сначала установите Router с `/v1/node/identity` на обоих узлах, затем повторно подтвердите их текущие `bootId`. В файл квалификации Gate добавьте объект `selectorBundleSha256` с SHA-256 трёх файлов кандидата: `haproxy.cfg`, `path_checks.lua`, `preflight.py`. Передайте штатному скрипту установки Gate параметры `--refresh-standby-pins --selector-bundle /абсолютный/путь/router-standby`. Проверка сверит хеши, синтаксис HAProxy и ответы обоих Router по обеим дорогам до остановки Gate.

Замена выполняется внутри обычного окна поставки после остановки приёма, завершения активных ходов, проверки пустых входов и остановки Gate. Предыдущие файлы остаются в `selector-before` в каталоге резервной копии. При ошибке старый комплект возвращается до восстановления Gate. Для проверки кандидата на Linux используйте `tests/ops/router_standby_canary.py` в пространстве имён сети только с loopback.

## Отдельный транспорт вложений (Gate #161)

У каждого Router два входа на loopback Gate. В таблице порты перечислены в порядке Codex / Claude.

| Назначение | Вход Gate в HAProxy | Напрямую к Router | Через FI к Router |
| --- | --- | --- | --- |
| Запросы хода, события, отправка результатов инструментов и чтение квитанций | 38765 / 38768 | 8765 / 8768 | 28765 / 28768 |
| POST вложения, PDF-документа, адаптивной загрузки | 31665 / 31668 | 17665 / 17668 | 27665 / 27668 |

Поле узла `url` задаёт первый вход, `file_url` — второй. Старые реестры с пустым или отсутствующим `file_url` работают через прежний транспорт. Оба процесса Router слушают те же внутренние порты 8765 и 8768. Codex и Claude по-прежнему делят соединение своего класса на каждой дороге. У каждого класса собственные процессы OpenSSH и TCP-сокеты на прямой дороге и на обоих участках ProxyJump. Поэтому ретрансляция пакета с частью файла больше не заставляет тот же TCP-поток удерживать квитанцию. Каналы по-прежнему делят полосу провайдера, интерфейсы хостов и обработчики Router.

Селектор опрашивает каждый путь по его собственному входу и на каждой дороге проверяет закреплённые nodeId и bootId. Если прямой управляющий путь обнаружил чужой процесс, файловый вход также закрывается. Обрыв загрузки после отправки сверяется по первоначальному ключу квитанции через управляющий вход. Селектор может выбрать FI для нового соединения. Переключение сохраняет исходную команду и её ключ.

Для включения установите `atlas-router-files-{direct,fi}.service` в `/etc/systemd/system`, `ssh_config_files` и `file-lanes.env` в `/etc/atlas/router-standby`. Поставьте `file-lanes.conf` в каталоги drop-in служб `atlas-router-selector` и `atlas-router-standby-enrol`. Все новые порты привязаны к loopback. Для FI используются действующие ограниченные ключи и проверенные host keys. В свободное окно запустите две файловые службы и выполните штатную активацию с `--refresh-standby-pins --selector-bundle <каталог> --file-lanes`. Она сверяет общий boot по четырём физическим входам, сохраняет прежние адреса и дожидается ответа через оба селектора для каждого узла. При ручном откате сначала верните предыдущий реестр и селектор под штатным запретом новых ходов. После проверки квитанций остановите дополнительные SSH-службы.
## Диагностика обрыва при создании сессии

Начиная с Gate 0.4.50, в журнале службы `atlas-gate` строки `session_create ingress_start` и `ingress_end` показывают границы отдельной попытки Harness на уровне ASGI. Сопоставляйте их по `attempt`. Строка `binding` связывает попытки одним безопасным отпечатком `keyTag` и показывает состояние прежней записи. Возврат обработчика подтверждает только передачу ответа серверу ASGI. При отмене на стороне Harness сверяйте также его события и access log nginx.

Для каждого исходящего POST создания в прямом HTTP-транспорте Gate генерирует отдельный `X-Atlas-Trace-Id`. Строки `wire_start` и `wire_end` связывают его с входящей попыткой. `marksMs` — метки от начала исходящего вызова по монотонным часам. При потере ответа смотрите, закончилась ли отправка тела, начался ли приём заголовков, какой была цепочка исключений и есть ли тот же `traceId` на Router. `eof_before_headers` означает, что HTTP-клиент прочитал EOF до заголовков ответа. Инициатора закрытия устанавливают по записям соответствующей стороны и сетевым наблюдениям. При обрыве на уже открытом сокете до получения заголовков httpcore может не сообщить локальный порт, тогда он указан как `None`.
