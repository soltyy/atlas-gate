# Резервный путь Gate через Финляндию

Резерв включается отдельно по решению оператора. Оба пути заканчиваются на тех же процессах Router на `vdska`. Gate сохраняет `node_id`, привязки сессий и журнал команд. Рабочий прямой туннель обслуживает `atlas-gate-link.service`.

| Узел | Рабочий порт на Gate | Порт на Gate через FI | Порт селектора для проверки | Назначение на `vdska` |
| --- | ---: | ---: | ---: | --- |
| `vdska-codex` | 8765 | 28765 | 38765 | `127.0.0.1:8765` |
| `vdska-claude` | 8768 | 28768 | 38768 | `127.0.0.1:8768` |

Все порты таблицы слушают на `127.0.0.1`. До явного изменения адресов Gate его рабочие запросы продолжают идти напрямую.

## Подготовка доступа

На Gate нужен подтверждённый SSH-профиль промежуточного узла FI. Закрепите проверенные ключи хостов FI и `vdska`. Для конечного узла укажите тот же `HostKeyAlias`, под которым уже закреплён его ключ при прямом доступе. Настройте `ProxyJump` через FI, проверку `StrictHostKeyChecking yes` и отдельное SSH-соединение для резервного транспорта. На FI разрешите выделенной учётной записи проброс только к SSH-порту существующего `vdska`. Конечный SSH-проброс на `vdska` ведёт к двум loopback-портам из таблицы. Клиентский ключ для входа на `vdska` хранится на Gate. Пересылка SSH-агента выключена.

Туннель и селектор запускаются на Gate под непривилегированными служебными пользователями. Предоставьте проверке существующие токены соответствующих Router через одобренное хранилище секретов служб. Финскому узлу достаточно TCP-проброса к SSH.

Когда администратор выдаст подтверждённый профиль конечного узла с настроенным `ProxyJump`, команда под служебным пользователем открывает отдельные резервные порты:

```sh
ssh -NT -o BatchMode=yes -o StrictHostKeyChecking=yes -o ForwardAgent=no \
    -o ExitOnForwardFailure=yes -o ControlMaster=no -o ControlPath=none \
    -L 127.0.0.1:28765:127.0.0.1:8765 -L 127.0.0.1:28768:127.0.0.1:8768 \
    "$ROUTER_VIA_FI_PROFILE"
```

Укажите в `ROUTER_VIA_FI_PROFILE` имя проверенного профиля конечного Router. Проверьте настройки строгой проверки ключа и ограничений отдельно в профиле промежуточного узла FI. Успешный запуск SSH подтверждает занятие локальных портов. Доступ до Router проверяется следующим шагом.

## Проверка до подключения Gate

1. Поднимите резерв на выделенных портах `28765` и `28768`. Служба прямого туннеля продолжает обслуживать рабочие порты.
2. Для каждого префикса `CODEX_` и `CLAUDE_` задайте `NODE_ID`, `DIRECT_PORT`, `STANDBY_PORT`, `LISTEN_PORT` по таблице и передайте `CHECK_TOKEN` через секреты службы. В этом окружении выполните `python3 preflight.py` из каталога инструкции. Проверка читает защищённый `GET /v1/node` на прямом и резервном адресах каждого Router. Для каждой пары требуется совпадение `nodeId` и `bootId` и соответствие ожидаемому `NODE_ID`.
3. Только после успешной сверки передайте выданные `CODEX_BOOT_ID` и `CLAUDE_BOOT_ID` процессу селектора через временный файл окружения службы в `/run`. Запись файла должна быть доступна только администратору. Значения относятся к текущим процессам Router.
4. В окружении службы проверьте конфигурацию командой `haproxy -c -f haproxy.cfg`. Запустите контрольный экземпляр HAProxy с этой конфигурацией и проверьте защищённый `GET /v1/node` на портах `38765` и `38768`. Для испытания отказа выделите отдельный экземпляр селектора с собственными свободными портами и недоступным прямым входом. Оба контрольных запроса должны вернуть сверенные пары через FI. Зафиксируйте результат по обоим Router перед включением в Gate.

## Переключение и возврат

Каждый дополнительный запрос к `/v1/node` читает состояние SDK. Выделенный селектор по умолчанию проверяет каждый путь раз в 30 секунд. Перед переключением измерьте влияние этих проб на оба Router при реальной нагрузке и проверьте время обнаружения отказа. Период задаёт `ROUTER_PATH_CHECK_INTERVAL`. Он определяет частоту опроса, а исход команды определяется квитанцией. Ответ проверки ограничен 32 КиБ. Для данных рабочего потока `timeout client` и `timeout server` равны нулю. HAProxy 2.8 сообщает об этом предупреждением при проверке конфигурации.

В свободное окно сохраните текущие адреса узлов и проверьте отсутствие активных ходов по штатной процедуре поставки. На этапе переключения замените только `url` соответствующих узлов Gate на `http://127.0.0.1:38765` и `http://127.0.0.1:38768` и примените конфигурацию штатным способом. Проверьте опрос обоих узлов самим Gate и снимите свою паузу приёма новых ходов. При откате верните `http://127.0.0.1:8765` и `http://127.0.0.1:8768` тем же способом, проверьте оба узла и возобновите приём.

Селектор выбирает путь для нового TCP-соединения. После разрыва уже открытого потока приложение дочитывает события исходного хода с последнего подтверждённого `seq`. Для команды с неопределённым исходом Gate запрашивает квитанцию на исходном Router по прежнему ключу. Переключение транспорта не инициирует повторный POST или запуск инструмента.

При плановом перезапуске Router меняется `bootId`. Прямой путь остаётся доступен, резерв для этого узла ждёт новой сверки. Заново выполните проверку обеих пар, обновите временное окружение и примените его к селектору. Сверьте идентичность каждого узла через контрольные порты.
